# API Sentinel (eBPF)

## Overview

This module is responsible for capturing HTTP network traffic directly from the Linux kernel. Instead of relying on application logs or middleware, it observes network communication at the kernel level, allowing HTTP requests and responses to be captured with very low overhead.

The module is implemented using eBPF in C and a Rust userspace application. The eBPF program captures the raw payloads, while the Rust application receives the captured events through a Ring Buffer and converts them into structured JSON records.

---

# Status

The eBPF module has been successfully implemented and tested on Ubuntu 26.04 LTS. It captures both incoming HTTP requests and outgoing HTTP responses generated by the FastAPI/Uvicorn application. Each captured event contains metadata such as timestamp, process ID, process name, connection identifier, payload length, traffic direction, and the corresponding payload.

---


# eBPF

Extended Berkeley Packet Filter (eBPF) allows small programs to run safely inside the Linux kernel. It provides direct visibility into kernel events without modifying the kernel source code or creating traditional kernel modules.

In this project, eBPF is responsible for observing TCP communication and extracting HTTP payloads directly from the kernel before forwarding them to userspace.

---

# Why eBPF?

Traditional application logging only records information that the application explicitly chooses to log. In contrast, eBPF captures network activity directly from the kernel, making it possible to observe traffic independently of the application logic while introducing very little performance overhead.

---

# kprobes

kprobes are dynamic kernel instrumentation mechanisms that allow eBPF programs to execute whenever specific kernel functions are called.

This project uses kprobes to intercept the Linux TCP networking functions responsible for receiving and sending data.

### tcp_recvmsg

The `tcp_recvmsg` kernel function is used to receive data from the network.

In this project, it is used to capture incoming HTTP requests. Since the userspace buffer is populated only after the kernel completes the receive operation, a kprobe and a corresponding kretprobe are used together. The entry probe stores the required context, while the return probe reads the completed request payload after the kernel has copied it into userspace.

### tcp_sendmsg_locked

The `tcp_sendmsg_locked` kernel function is responsible for sending TCP data.

It is used to capture outgoing HTTP responses. Since the response buffer already exists before transmission, the payload can be read directly when this function executes.

---

# Ring Buffer

The Ring Buffer is the communication mechanism used between kernel space and userspace.

After capturing a request or response, the eBPF program writes the event into the Ring Buffer. The Rust application continuously polls this buffer and immediately receives every event without repeatedly querying the kernel.

A Ring Buffer was chosen because it provides low-latency communication, supports high event throughput, and introduces less overhead than older mechanisms such as perf buffers.

---

# libbpf

libbpf is the official userspace library for loading and managing eBPF programs.

It handles loading the compiled eBPF object, creating kernel maps, attaching kernel probes, and managing communication with kernel resources.

---

# libbpf-rs

libbpf-rs is the Rust binding for libbpf.

It allows the Rust application to interact with the eBPF program using native Rust APIs while internally relying on libbpf for kernel interactions.

---

# Rust Userspace Application

The Rust application acts as the userspace component of the module.

Its responsibilities include:

- Loading the eBPF program.
- Attaching all kernel probes.
- Creating and polling the Ring Buffer.
- Receiving captured events from the kernel.
- Converting binary event data into structured JSON records.

The Rust application performs only event collection and formatting. It does not modify or analyse the captured payloads.

---

# Event Structure

Each captured event contains:

- Timestamp
- Connection Identifier
- Process ID
- Process Name
- Traffic Direction (Request or Response)
- Payload Length
- Raw Payload

The connection identifier is used to associate requests and responses that belong to the same TCP connection, while the payload stores the raw HTTP data captured from the kernel.

---

# Output

For every captured request or response, the Rust application generates a structured JSON record containing all relevant metadata and the captured payload encoded in hexadecimal format.

This JSON output provides a consistent representation of captured network traffic while preserving the original payload exactly as it was observed inside the Linux kernel.
